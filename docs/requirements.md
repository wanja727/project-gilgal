## 확정 변경 사항 (2026-10-19 검토 반영)

> 아래 결정은 이 문서의 원래 요청보다 우선한다. 본문 해당 절에도 `[변경]` 표시로 반영했다.
> 설계 근거는 `docs/architecture.md` ADR 참조.

1. **Supabase 프로젝트 완전 분리** — 길갈은 신규 Supabase 프로젝트(별도 DB 인스턴스)를 사용한다. 인증·세션 테이블과 서비스 데이터를 모두 독립 관리하고, Selah 운영 DB에는 어떤 DDL/DML도 하지 않는다. Selah DB와 실시간 연동하지 않는다.
2. **인증·셀 재사용 방식** — 같은 카카오 OAuth 앱을 사용하고, 길갈 자체 Auth.js 테이블·세션을 둔다. 기존 회원은 **카카오 고유 ID(회원번호)** 로 연결하며, Selah의 실명·셀 정보는 오픈 전 1회 최소 항목만 이관한다. (DB가 달라 내부 `user.id` 는 서로 다르다.)
3. **통독 일정·공개 정책 확정** — 13절 참조. 12/5 이후에도 모든 장을 계속 읽고 완료할 수 있다. 공개 여부는 KST 기준 서버에서 검증한다.
4. **성경 본문** — ~~Mock(개발)/원문 링크(운영)~~ **[2차 변경]** 여호수아 개역개정 본문을 **길갈 서비스 내부에서** 장·절 구분해 표시하고, 외부 사이트 이동 없이 읽기→완료→댓글을 진행한다. 이용 허락 확인 전에는 수집·저장·재배포하지 않고 `BibleTextProvider` + Mock 본문으로 구현하며, 허락 후 정적 파일 또는 DB로 24장을 연결한다. 15절 참조.
5. **여정 지도 기본 버전은 Phase 1** — 20절 참조.
6. **Selah 프로젝트 보호** — `C:\side-project\project-selah` 의 코드·DB·환경변수·배포 설정은 읽기 전용 참고 자료로만 사용한다.

### 2차 확정 (2026-10-19)

7. **셀 편성** — Selah가 관리하던 셀 목록과 셀원 명단을 초기 데이터로 사용한다. 11월 기준 최신 여부는 확인하지 않는다. 이관 후에는 길갈 DB에서 관리하며, 잘못된 셀 정보는 운영자가 Supabase에서 직접 수정한다(관리자용 셀 편성 화면은 MVP 제외).
8. **온보딩(Selah 방식 재사용)** — ① 카카오 로그인 → ② 이관 명단에서 카카오 회원번호 일치 확인 → ③ 일치 시 실명·셀 자동 설정 → ④ 불일치 시 Selah 실명 매칭 로직 참고 → ⑤ 자동 확인이 안 되면 본인이 셀을 직접 선택 → ⑥ 셀은 기존 셀 목록에서만 선택(자유 텍스트 없음) → ⑦ 실명·셀 선택이 끝나면 온보딩 완료. 다른 사용자 계정을 임의로 연결할 수 없도록 카카오 식별자·실명 매칭 보안을 검토한다.
9. **Supabase 개발 환경** — 길갈 Supabase 프로젝트 하나만 만들어 개발·초기 테스트에도 사용한다(`gilgal-dev` 없음). 마이그레이션 SQL은 적용 전 검토·승인, 테스트 데이터는 실제 데이터와 구분, 운영 데이터에 영향을 주는 테스트·삭제는 승인 후 실행, DB 연결은 환경변수 기반, `drizzle-kit push` 대신 버전 관리되는 마이그레이션 사용.
10. **도메인** — 커스텀 도메인 없이 Vercel 기본 도메인(예상 `https://project-gilgal.vercel.app`, 실제 할당 주소 기준). 카카오 Redirect URI는 로컬 `http://localhost:3000/api/auth/callback/kakao`, 운영 `https://<실제-vercel-도메인>/api/auth/callback/kakao` 를 기존 URI 변경 없이 추가.
11. **기타 확정** — 공동체 진행도 분모 = 길갈 온보딩 완료 사용자, 사용자 표시 이름 = 실명, 공개된 장에는 로그인한 사용자 누구나 댓글 작성, 12/6 이후에도 종료일 없이 읽기·완료·댓글 가능.

### 3차 확정 (2026-10-24, 디자인 시안 v5 반영)

12. **서비스 표기명 "에벤"** — 화면에 보이는 이름만 바꾼다(`lib/brand.ts`). 저장소·DB·도메인 이름은 gilgal 그대로.
13. **디자인 톤** — 시안 v5 의 남색(navy) 하나로 고정. 제목·성경 본문은 고운바탕, 나머지는 Pretendard(자체 호스팅). 톤 전환 기능은 만들지 않는다.
14. **내 위치** — 1장부터 빠짐없이 이어서 읽은 마지막 장(1·2·3·5장 → 3장). 아무 장도 안 읽었으면 1장 앞 출발점. 칸 하나하나는 실제 완료 여부로 표시. "깃발까지 N장" = 오늘까지 공개된 장 중 안 읽은 장 수.
15. **도착 순서** — "오늘 N장까지 읽은 사람"은 오늘 공개된 장의 완료 시각 순. 상위 3명은 1st/2nd/3rd(이름·셀·시각), 4번째부터는 아바타 몇 개와 인원수, 내 순위는 맨 아래 내 줄. [변경] 핵심 3("출석 경쟁이 아님")과 긴장이 있으나 운영자 확정. 완료하지 않은 사람의 명단은 여전히 보여 주지 않는다.
16. **셀 카드** — 기준 장까지 온 셀원은 선명하게(이름 표시), 아직인 셀원은 이름 없이 흐린 아바타.
17. **나눔(댓글·공감)을 오픈 전에 포함** — 작성·공감·본인 수정/삭제·운영자 숨김, 나눔 탭.
18. **지도 데이터** — 시안의 장별 장소·제목·장면 설명·아이콘을 `lib/journey` 설정으로 통합(문구는 초안, 교회 검토 후 수정). 13~22장은 대표 장소에 묶고 지파별 영역 표시는 Phase 2.
19. **[변경 2026-10-26] 개관 탭 추가** — 하단 탭은 오늘 · 여정 · 개관 · 나눔 · 나. 교회(청년캠프1)가 준 여호수아 개관 글(표어 "성결"·배경·네 부분·수 1:8)을 그대로 보여 준다. [변경 2026-10-26] ACT 구분·이름을 개관(목사님 작성)에 맞춘다: 1–5 들어가다 · 6–12 정복하다 · 13–21 분배하다 · 22–24 언약을 새롭게 하다. 22장은 ACT 4로 옮기되 지도 표현(동쪽 지파 귀환)은 그대로.

## 작업 요청 프롬프트

### 프로젝트 개요

교회 공동체에서 진행할 **여호수아서 온라인 공동체 통독 서비스**를 새로 개발하려고 한다.

기존에 개발했던 프로젝트인 \*\*Selah(셀라)\*\*의 사용자 인증 및 소속 셀 정보를 최대한 재사용하고, 그 위에 새로운 통독 서비스를 구축해줘.

단순한 성경 읽기 체크 앱보다는,

> **“공동체가 24일 동안 여호수아의 여정을 함께 걷는다.”**

라는 경험을 핵심 컨셉으로 잡고 싶다.

# 1. 먼저 기존 Selah 프로젝트 분석

구현부터 시작하지 말고, 현재 workspace/repository에 있는 **Selah 프로젝트 구조를 먼저 분석해줘.**

특히 아래 내용을 확인해줘.

- 로그인/회원 인증 방식
- 사용자 테이블 및 프로필 구조
- 사용자의 소속 셀 정보 저장 방식
- 셀 테이블 및 셀원 관계
- 로그인 세션 유지 방식
- Supabase Auth 사용 여부 및 연동 구조
- 공통 Layout / Header / Navigation 구조
- DB 접근 방식
- 기존 Supabase schema 및 migration 구조
- Vercel 배포 관련 설정
- 모바일 반응형 UI 구현 방식

이번 프로젝트에서는 가능하면 Selah의 인증/사용자/셀 정보를 **중복해서 새로 만들지 말고 재사용**하고 싶다.

다만 기존 코드를 무조건 복사하지 말고, 현재 구조를 분석한 후 가장 안전하고 유지보수하기 좋은 재사용 방법을 선택해줘.

~~기존 DB를 함께 사용할 수 있다면 기존 사용자와 셀 정보를 연결하고, 새 서비스에 필요한 데이터만 별도 테이블로 추가하는 방향을 우선 검토해줘.~~

**[변경]** 길갈은 신규 Supabase 프로젝트를 사용하며 Selah DB를 공유하지 않는다. 셀 편성은 Selah의 셀 목록·명단을 기준으로 하고, 온보딩은 Selah 방식을 최대한 재사용한다(상단 2차 확정 7·8). 같은 카카오 OAuth 앱으로 로그인하고, 카카오 고유 ID로 기존 회원을 연결한다. Selah의 실명·셀 정보는 오픈 전 1회 최소 항목만 이관하고, 이후 셀 변경은 길갈에서 관리한다. Selah 운영 DB에 실시간으로 의존하거나 복잡한 동기화 구조를 만들지 않는다.

# 2. 서비스 일정

통독 대상은 **여호수아서 전체 24장**이다.

정식 통독 기간:

- 2026년 11월 2일(월) \~ 11월 28일(토)
- 주일 제외
- 월요일 \~ 토요일 진행
- 매일 여호수아 1장씩
- 총 24일 / 24장

즉,

- 11/2 → 여호수아 1장
- 11/3 → 2장
- ...
- 11/28 → 24장

으로 정확히 매핑한다.

추가로

**2026년 11월 30일(월) \~ 12월 5일(토)**

은 `Catch-up 기간`으로 운영한다.

이 기간에는 새로운 장이 열리는 것이 아니라, 사용자가 정식 기간 동안 읽지 못했던 장을 보충해서 읽을 수 있도록 한다.

# 3. 서비스 핵심 컨셉

일반적인 체크리스트형 통독 앱이 아니라,

> **“오늘 한 장을 읽으면 우리의 여정이 한 걸음 진행된다.”**

는 경험을 제공하고 싶다.

여호수아서 자체가

**요단 동쪽 → 요단강 → 길갈 → 여리고 → 아이 → 가나안 중앙 → 남부 → 북부 → 땅 분배 → 실로 → 세겜**

으로 이어지는 공간적 흐름을 가지고 있으므로, 사용자가 매일 한 장씩 읽을 때마다 **실제 여호수아의 여정을 지도 위에서 따라가는 경험**을 제공하고 싶다.

또한 개인 혼자 읽는 것이 아니라,

> **“오늘도 공동체가 함께 읽고 있다.”**

는 느낌이 강하게 들었으면 좋겠다.

요단을 건너

# 7. 여정 지도

이번 서비스의 가장 중요한 시각적 요소다.

실제 Google Maps 같은 현실 지도 UI보다는,

**성경 시대의 여정을 표현하는 일러스트형 / 미니멀한 SVG 지도**

형태를 우선 고려해줘.

지도에는 장에 따라 다음과 같은 주요 지점이 나타날 수 있다.

- 요단강
- 길갈
- 여리고
- 아이
- 에발산
- 기브온
- 헤브론
- 하솔
- 실로
- 세겜

모든 작은 도시를 표시할 필요는 없다.

사용자가 전체 흐름을 쉽게 이해하는 것이 우선이다.

고대 도시의 정확한 위치가 논쟁적인 경우가 있으므로 실제 GPS 지도처럼 “정확한 역사적 위치”를 단정해서 표현하지 말고, **교육용 schematic map**으로 구현해도 좋다.

각 DAY에 필요한 위치 정보는 별도 데이터로 관리해줘.

예:

```
type JourneyDay = {
  day: number;
  chapter: number;
  title: string;
  act: number;
  location?: string;
  description?: string;
  mapX?: number;
  mapY?: number;
};
```

하드코딩을 여러 컴포넌트에 분산시키지 말고 하나의 configuration 파일 또는 DB에서 관리할 수 있게 해줘.

# 9. 사용자 아바타 (DiceBear Marbles)

사용자별 아바타는 **DiceBear의 `marbles` 스타일**을 사용해 자동 생성해줘.

중요한 요구사항:

- 사용자가 처음 로그인하면 별도 업로드 없이 자동으로 아바타가 생성되어야 한다.
- 아바타는 사용자별로 **고유하지만 고정된 결과**가 나오도록 seed 기반으로 생성한다.
- [변경 2026-10-24] 아바타 색은 서비스 톤(남색 계열) 팔레트로 고정한다.
- [변경 2026-10-20] 사용자가 원하면 ~~`/journey`~~ `/me`(나 탭) 에서 아바타를 섞어(새 seed) 미리 보고 저장할 수 있다. 저장 전까지는 기존 아바타가 유지된다(ADR-020).
- 예: `user.id`, `nickname`, 혹은 별도 저장된 avatar_seed 활용
- 기본 MVP에서는 **의상/치장/꾸미기 기능은 구현하지 않는다.**
- 다만 추후 확장을 고려해서 아바타 관련 구조는 확장 가능하게 설계해줘.
- 아바타는 프로필 영역뿐 아니라 **메인 화면 / 셀 화면 / 참여 현황 UI**에서도 사용한다.

예를 들면:

- 메인 화면 상단의 내 프로필
- 오늘 여정을 완료한 사람들 목록
- 우리 셀 참여 현황
- 댓글 작성자 표시

DiceBear 라이브러리를 직접 붙일지, SVG/URL 생성 방식으로 처리할지는 현재 프로젝트 구조에 맞춰 결정해줘.

# 10. 메인 화면의 아바타 기반 참여 시각화

메인 화면에서 공동체가 함께 읽고 있다는 느낌을 주기 위해, **아바타 기반 참여 현황 UI**를 넣고 싶다.

예를 들어 아래와 같은 느낌을 검토해줘.

## 오늘 여정을 마친 사람들

- 오늘 읽기 완료한 사람들의 Marbles 아바타를 작은 원형 리스트나 클러스터 형태로 보여준다.
- 너무 많은 경우 전부 보여주기보다 일부만 보여주고 `+N명` 표시 가능
- 예:
  - “오늘 37명이 여정을 마쳤어요”
  - 아바타 8개 + `+29`

## 아직 시작하지 않은 사람들

- 읽지 않은 사람도 시각적으로 보여줄 수 있으면 좋겠다.
- 다만 공개적으로 압박을 주는 느낌은 피하고 싶다.
- 따라서 다음 원칙을 고려해줘:
  - 전체 공동체 기준에서는 익명/요약 중심
  - 셀 단위에서는 어느 정도 아바타 기반으로 보여줄 수 있음
  - 노골적으로 “미완료자 명단”처럼 보이지 않게 함
  - 표현 문구도 부드럽게: “아직 여정을 시작하지 않은 동행자들” 정도

예:

- “아직 12명의 동행자가 오늘 여정을 시작하지 않았어요.”
- 흐리게 처리된 아바타 몇 개 + `+N`

이 기능의 목적은 감시가 아니라 **함께 읽도록 독려하는 분위기**를 만드는 것이다.

구체적인 표현 방식은 UX 관점에서 더 나은 대안이 있으면 제안해줘.

# 11. 공동체 진행도

중요한 것은 개인 통독만이 아니라

**“함께 읽고 있다”**

는 느낌이다.

오늘의 참여 인원을 보여준다.

예:

```
오늘 87명이 함께 걷고 있어요.
```

또는

```
87 / 124명이 오늘 말씀을 읽었습니다.
```

가능하다면 자신의 셀 진행도도 함께 보여준다.

예:

```
우리 셀
8 / 11명 완료
```

단, 다른 사용자에게 개인별 미완료자를 노골적으로 보여주어 출석 압박이 생기지 않도록 한다.

기본적으로는 **숫자 + 아바타 기반의 부드러운 진행도 표현**을 사용한다.

셀 정보는 Selah의 기존 소속 셀 데이터를 사용한다. **[변경]** 단, 실시간 조회가 아니라 오픈 전 길갈 DB로 이관한 셀 데이터를 사용한다.

# 12. 개인 진행도

개인은 24개의 DAY 진행 상태를 확인할 수 있다.

다만 일반적인 체크리스트보다 지도와 연결된 형태가 우선이다.

예:

```
나의 여정
● ● ● ● ● ● ● ○ ○ ○ ...
7 / 24
```

읽지 않은 날을 `결석`처럼 표현하지 않는다.

대신

**“아직 걷지 않은 길”**

이라는 서비스 언어를 사용한다.

예:

```
아직 걷지 않은 길이 2개 있어요.
```

# 13. Catch-up 기간

11월 30일 \~ 12월 5일에는 새로운 DAY가 진행되지 않는다.

미완료된 장이 있는 사람에게

```
아직 걷지 않은 길이 있습니다.

여정을 완성하러 갈까요?
```

와 같은 화면을 보여준다.

미완료 목록을 제공하고 원하는 장을 선택해서 읽을 수 있도록 한다.

예:

```
아직 걷지 않은 길

DAY 7 — 여호수아 7장
DAY 14 — 여호수아 14장
```

모두 완료하면 24일 완주 화면을 볼 수 있다.

### [변경] 일정·공개 정책 확정

1. 지난 날짜의 장은 언제든 다시 읽을 수 있다.
2. 이미 공개된 장은 정식 통독 기간 중에도 언제든 보충해서 완료할 수 있다.
3. 일요일에도 이미 공개된 장을 읽거나 완료할 수 있다.
4. 미래 날짜의 장은 예정된 공개일 전까지 완료할 수 없다.
5. Catch-up 기간은 읽기 권한을 처음 주는 기간이 아니라, 미완료자에게 추가 완주 기회를 주는 기간이다. Catch-up 기간에는 새로운 장을 공개하지 않는다.
6. **12월 5일 이후에도 모든 장을 계속 읽고 완료할 수 있다.**
7. 캠페인 종료 후에도 개인 진행도, 여정 지도, 완주 회고, 기존 댓글을 이용할 수 있다.

일정과 공개 여부는 KST 기준으로 서버에서 검증한다.

# 14. 댓글 / 공감 기능

기존에 생각했던 “오늘의 한 단어” 기능은 제외하고, 대신 **해당 일자의 성경 본문 하단에 댓글 기능**을 넣고 싶다.

이 댓글은 사용자가 오늘 본문을 읽고 느낀 점을 자유롭게 나누는 공간이다.

중요한 요구사항:

- 해당 DAY / 해당 장 단위로 댓글이 달린다.
- 위치는 **오늘의 성경 본문 하단**
- 사용자는 댓글을 작성할 수 있다.
- 댓글 작성 시 작성자 아바타(DiceBear Marbles)가 함께 표시된다.
- 댓글에는 **좋아요 또는 공감 기능**이 있어야 한다.
- 공감 수는 표시한다.
- 한 사용자가 같은 댓글에 중복 공감하지 않도록 한다.
- 필요하면 공감 취소도 가능하게 한다.
- 정렬은 기본적으로 최신순 또는 공감순 중 적절한 방식을 제안해줘.
- MVP에서는 댓글 대댓글까지는 없어도 된다. 우선은 1-depth 댓글만 구현해도 된다.
- 댓글 삭제/수정 여부는 현재 구조와 운영 편의성을 고려해 제안해줘.
- 비방/과도한 내용에 대비해 최소한의 신고/숨김 설계를 고려해줘. MVP에서는 관리자 삭제 정도만 있어도 괜찮다.

이 댓글 기능은 **성경 해설 서비스가 아니라 공동체 나눔 공간**이라는 성격을 갖는다.

# 15. 성경 본문

성경 본문의 저작권 문제가 있을 수 있으므로 임의로 특정 한글 번역본 전문을 repository에 넣지 말아줘.

현재 프로젝트 또는 기존 Selah에서 성경 본문을 어떻게 처리했는지 먼저 확인하고,

적법한 데이터 소스 또는 기존에 사용 중인 방식이 있다면 그것을 따른다.

적절한 본문 데이터를 사용할 수 없는 경우 우선 UI와 데이터 구조를 구현하고 mock data를 사용한다.

그 경우 어떤 데이터 소스가 필요한지 README/TODO에 명확히 남겨줘.

### [변경] 개역개정 사용 방침

- 길갈은 **여호수아서 개역개정** 본문을 사용하고 싶다. 참고: 대한성서공회 성경읽기 페이지 (`https://www.bskorea.or.kr/bible/korbibReadpage.php?version=GAE&book=jos&chap=1&sec=1`).
- 원하는 UX: 서비스 안에서 본문 읽기, 장·절 구분, 모바일 가독성, 본문 하단 댓글·공감, 본문과 읽기 완료 상태의 자연스러운 연결.
- 개역개정은 저작권 보호 대상이다. 사이트에서 열람하는 것과 제3자 서비스가 복제·배포하는 것은 다른 문제로 구분한다.
- 본문 전문의 자동 수집·저장·재배포는 이용 허락과 제공 조건을 확인한 뒤에만 진행한다.
- 현재는 `BibleTextProvider` 인터페이스 + Mock 데이터 기반으로 구현하고, 적법하게 확보한 데이터를 DB 또는 정적 파일로 쉽게 교체 연결할 수 있게 한다.
- **[2차 변경]** 외부 링크 중심 방식은 사용하지 않는다. 여호수아 1~24장 본문을 길갈 내부에서 장·절 번호를 구분해 표시하고, 모바일에서 읽기 편한 디자인으로, 본문 아래 읽기 완료 버튼과 댓글·공감을 자연스럽게 연결한다. 원문을 확보하면 24장 전체를 손쉽게 연결할 수 있어야 한다.
- 이용 허락 관련 운영자 준비사항은 별도 TODO로 관리한다(`docs/architecture.md` 참조).

# 16. 데이터 모델

기존 Selah DB를 먼저 확인한 후 정확한 schema를 결정해줘.

**[변경]** 길갈은 독립 DB를 사용하므로 Auth.js 테이블, 사용자 프로필, 셀, 이관 명단을 길갈 DB에 직접 둔다. Selah 스키마는 참고만 한다.

새로운 테이블은 최소화한다.

개념적으로 필요한 것은 다음 정도다.

### 통독 캠페인

- `reading_campaign`

필드 예시:

- id
- title
- bible_book
- start_date
- end_date
- catchup_start_date
- catchup_end_date
- total_days
- active

### 일자별 정보

- `reading_day`

필드 예시:

- id
- campaign_id
- day_no
- chapter
- reading_date
- act
- title
- location
- map metadata

### 사용자 읽기 상태

- `reading_progress`

필드 예시:

- id
- campaign_id
- reading_day_id
- user_id
- completed_at

중복 완료 데이터가 생기지 않도록

- `UNIQUE(user_id, reading_day_id)`

제약조건을 고려한다.

### 사용자 아바타 정보

기존 사용자 profile 테이블에 넣을 수 있으면 재사용하고, 별도 테이블이 필요하면 최소한으로 설계한다. **[변경]** 길갈 DB의 `profile` 테이블에 둔다.

예:

- avatar_style (`marbles`)
- avatar_seed

단, 현재 구조에 맞게 더 자연스러운 방식이 있다면 그렇게 해도 된다.

### 댓글

- `reading_comment`

필드 예시:

- id
- campaign_id
- reading_day_id
- user_id
- content
- created_at
- updated_at
- deleted_at (soft delete를 원하면)

### 댓글 공감

- `reading_comment_reaction` 또는 `reading_comment_like`

필드 예시:

- id
- comment_id
- user_id
- created_at

중복 공감 방지:

- `UNIQUE(comment_id, user_id)`

실제 이름은 프로젝트 convention에 맞게 변경해도 된다.

# 17. 권한 / 보안

사용자가 클라이언트에서 userId나 cellId를 임의로 바꿔 다른 사람의 데이터를 수정할 수 없도록 해줘.

Supabase를 사용한다면 RLS 정책도 반드시 검토한다. **[변경]** 길갈은 Supabase Auth를 쓰지 않으므로 서버 계층 권한 검사 + Data API 차단/RLS 전면 거부로 방어한다(ADR 참조).

특히:

- 자신의 reading_progress만 생성/수정
- 자신의 댓글만 작성/수정/삭제 가능
- 자신의 댓글 공감만 생성/취소 가능
- 공동체 통계는 필요한 최소 범위만 읽기
- 개인별 민감한 진행상황은 무분별하게 노출하지 않기

를 고려해줘.

# 18. 관리자 기능

MVP에서 거대한 관리자 페이지는 필요 없다.

다만 최소한 configuration으로 다음 내용을 쉽게 수정할 수 있도록 만들어줘.

- 캠페인명
- 기간
- 장별 제목
- 지도 좌표
- 장소
- ACT
- 완료 메시지

가능하다면 DB 기반으로 관리하고,

초기 단계에서는 seed/config 파일 기반이어도 괜찮다.

중요한 것은 컴포넌트 내부에 24일 데이터를 흩어놓지 않는 것이다.

댓글 관리 측면에서는 최소한 아래를 고려해줘:

- 부적절한 댓글 숨김 또는 삭제를 위한 최소한의 관리자 대응 구조
- 향후 신고 기능 확장 가능성 고려

# 21. 중요한 개발 원칙

기존 Selah 코드와 DB를 충분히 분석한 후 작업한다.

내가 설명한 구조를 무조건 그대로 구현할 필요는 없다.

현재 코드베이스 기준으로 더 좋은 방법이 있다면 개선해서 적용해도 된다.

다만 임의로 서비스 컨셉을 크게 변경하지 말아줘.

특히 아래 다섯 가지는 유지한다.

### 핵심 1

**24일 동안 한 장씩 여호수아서를 읽는다.**

### 핵심 2

**읽기 진행도를 여호수아의 실제 이야기 흐름에 맞춘 ‘여정 지도’로 표현한다.**

### 핵심 3

**개인의 출석 경쟁이 아니라 공동체가 함께 걷고 있다는 경험을 강조한다.**

### 핵심 4

**성경 본문에 대한 AI 해석이나 신학적 해설을 서비스가 임의로 제공하지 않는다.**

### 핵심 5

**사용자 경험에서 Marbles 아바타가 자연스럽게 살아나도록 한다.**

# 22. 작업 진행 방식

바로 대규모 구현부터 하지 말고 먼저 repository를 조사한 뒤 다음 내용을 정리해줘.

1. 현재 Selah 프로젝트 구조
2. 재사용 가능한 부분
3. 새로 추가해야 하는 부분
4. 예상 DB schema
5. 라우팅 구조
6. 컴포넌트 구조
7. 여정 지도 구현 방식
8. DiceBear Marbles 아바타 적용 방식
9. 댓글 / 공감 기능 구조
10. 작업 순서

그 내용을 기반으로 구현을 시작해줘.

작업 중 기존 구조와 내가 요청한 요구사항이 충돌한다면 기존 구조를 억지로 변경하기보다, 현재 코드베이스에 가장 자연스러운 방법을 선택하고 그 이유를 설명해줘.

기능을 구현한 뒤에는 최소한 다음 시나리오를 직접 검증해줘.

- 기존 Selah 사용자가 로그인할 수 있는가
- 기존 사용자의 셀 정보가 정상적으로 표시되는가
- 사용자별 Marbles 아바타가 안정적으로 생성/표시되는가
- 오늘 날짜에 맞는 여호수아 장이 표시되는가
- 읽기 완료가 중복 저장되지 않는가
- 완료 후 진행도가 정상적으로 증가하는가
- 공동체/셀 통계가 정상적인가
- 메인 화면에서 완료자/미시작자 아바타 UI가 자연스럽게 표시되는가
- 댓글 작성이 정상 동작하는가
- 댓글 공감이 중복 없이 동작하는가
- 지나간 미완료 장을 Catch-up 기간에 읽을 수 있는가
- 24장을 모두 완료하면 완주 화면이 정상적으로 표시되는가
- 모바일 화면에서 주요 기능을 문제없이 사용할 수 있는가

마지막에는 구현한 내용, DB 변경사항, 필요한 환경변수, migration 실행 방법, 남아 있는 TODO를 README 형태로 정리해줘.
